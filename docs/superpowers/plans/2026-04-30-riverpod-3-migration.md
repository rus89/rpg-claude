# Riverpod 2.x → 3.x Migration Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Unblock `dart run build_runner build` by upgrading the Riverpod ecosystem from 2.x to 3.x so it pulls in `analyzer ^8.0.0`, which supports Dart 3.11 dot-shorthand AST nodes (`DotShorthandInvocation`).

**Architecture:** Codegen is currently broken because `riverpod_generator 2.6.5` pins `analyzer < 8.0.0`, but the Dart 3.11 SDK emits `DotShorthandInvocation` AST nodes that the older analyzer's `BundleWriter` can't serialize, causing every build_runner invocation to crash on the first input file. The migration is constrained to the riverpod stack — every other dependency stays put. The fix is one pubspec edit + one rename across 12 sites + an audit of two `.value!` usages whose error-path semantics changed in 3.x.

**Tech Stack:**
- `flutter_riverpod ^3.3.0` (currently `^2.6.1`)
- `riverpod_annotation ^3.0.3` (currently `^2.6.1`)
- `riverpod_generator ^3.0.3` (currently `^2.6.1`, dev dep)
- `riverpod_lint ^3.1.0` (currently `^2.6.1`, dev dep)
- `analyzer ^8.0.0` (transitive, currently `7.6.0`)
- `_fe_analyzer_shared ^91.0.0` (transitive, currently `85.0.0`)

> Versions above are the floor caret constraints for pubspec.yaml. The pub solver may pick higher patch/minor releases; that is fine. Do NOT edit pubspec to pin exact versions — use `^` ranges.

> **Open question for Milan**: `pub outdated` shows the solver currently lands on `flutter_riverpod 3.1.0` + `riverpod_annotation 4.0.0` (a hybrid 3.x/4.x). The 3.x→4.x changelog only changes the *generator* (`Generated providers are no-longer constant`); the runtime APIs are identical between 3.x and 4.x. This plan targets the **3.x line throughout** for consistency and rolls back the generated `_$Hash` semantics. If the solver insists on `riverpod_annotation 4.x`, accept it — the migration code below works for both. The migration changes do **not** depend on which line we land on.
